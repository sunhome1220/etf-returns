# 重構：何時提、怎麼提、怎麼做

## 1. 何時提出建議（自動檢查）

每次改完程式、commit 之前，執行 `python3 tools/code_size.py`。符合下列任一項，就在回覆最後**附上重構建議**：

- 單一檔案超過 **1000 行**，或單一函式超過 **120 行**（`tools/code_size.py` 會列出來）。
- **同一段邏輯第二次出現**：要改兩個地方才能完成一件事（例如兩頁都有的匯出、即時報價）。
- 改一個功能時，必須同時改一個「產生出來的檔案」或另一份複製品（例如以前的 template.html／returns.html）。
- 修一個 bug 時發現同樣的 bug 也藏在另一份複製的程式裡。

**只提建議、不要自己動手**：重構不是使用者這次要的東西，要先問。同一個問題已經提過、使用者說先不用，就不要每次都提；等它明顯變得更嚴重（例如又多了一份複製）再提。

## 2. 建議怎麼寫

- 依「效益 ÷ 風險」排序，每項寫清楚：
  - 現況哪裡不好（具體檔名、行數、重複幾處）；
  - 改法；
  - 風險，以及要怎麼驗證畫面與功能不變。
- 註明哪些**不建議動**、為什麼（例如 Python 與 JS 各一份計算是必要的，用測試確保一致即可）。
- 最後問使用者要做哪幾項。

## 3. 執行重構的步驟

1. **先有安全網**：重構前先確認 `python3 -m unittest discover -s tests` 與 `node tests/web_test.js` 都通過；要動的功能如果沒有測試，先補測試再重構。
2. **保留改之前的輸出**：會影響畫面或圖片的，先存一份改之前的結果（例如匯出圖片），改完逐像素比對，差異要能逐一說明。
3. **一次只做一種變動**：搬移程式時不要順便改邏輯；需要修的 bug 另外說明。
4. **共用的放對地方**：
   - 兩頁共用的瀏覽器程式：`market.js`（資料、報價、日期）、`export.js`（匯出圖片），或新增同類的共用檔，並在 `CLAUDE.md` 的檔案表登記。
   - Python 與 JS 都要算的：各寫一份，在 `tests/fixtures/calc_cases.json` 加案例確保一致。
5. **收尾**：
   - 改了 js／css／`template.html` 後執行 `python3 build.py --html-only`（更新版本號）。
   - 新檔案加進 `sw.js` 的快取清單。
   - 更新 `CLAUDE.md`。
   - 加一筆 CHANGELOG，寫「功能不變」。
6. **驗證**：
   - 本機兩組測試都要通過。
   - 動到 `build.py` 時，對分支觸發「更新報酬率」，確認排程輸出正確。
   - PR 上的「測試」workflow 通過才合併。
